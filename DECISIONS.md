# Decisions Log — Slip Flow (Deploy or Die, Track A)

Running record of every meaningful decision, in order. Continues the same discipline used on the Track B build (`whatswithavi/gdg_deploy_or_die`), which stays untouched as a fallback submission.

## Why this project exists

Started as a Track B submission (AI Code Review Assistant — done, CI green, tagged `v1.0.0`, kept as-is). Mid-build, a fully pre-written Track A plan (OCR raw-material slip digitization, human-in-the-loop approval, `SlipExtractionAgent`/`QueryAgent`, audit trail) plus a dedicated Firebase project (`gdgdeployordie`) and an existing Flutter design system (`aavii_website`) became available. Track A's design is genuinely stronger on the 30%-weighted Agent Engineering and 25%-weighted Architecture judging criteria (two real agents, human approval gate, audit log, citation-only answers), so we're attempting the pivot with Track B kept as an explicit, working fallback if this doesn't finish in time. Full tradeoff reasoning is in the approved plan; the short version:

- **Flutter Web, not native-only**: the source `ARCHITECTURE.md` specified React/PWA. Flutter Web keeps the same Dart codebase (so it's still "the Flutter app"), while staying Playwright-testable and buildable to Android later via the already-registered app.
- **Gemini multimodal for OCR, not Google Cloud Vision**: one call does OCR + structured extraction, reusing the exact Gemini key/model already proven working in Track B — avoids a second untested credential path.
- **A brand-new repo, not `aavii_website` itself**: that repo is a large, unrelated, months-old personal project (a study app) with its own git history and likely-private materials — using it as the hackathon repo would hurt the "clean Git history" story and could force private content public. Only specific reusable files were ported (see below), as fresh files, not a dependency on the old repo.

## Build log

- **Part 1**: `flutter create` (web + android targets) in a fresh repo, `whatswithavi/gdg-slip-flow`. Confirmed web build works before committing. Ported the `vault-ui-soften` Claude Code skill from `aavii_website/.claude/skills/` for consistent UI styling on new screens.
- **Part 2**: Ported the design system — `app_colors.dart`, `app_theme_controller.dart` (dark mode, theme-aware color extension) verbatim; `BrutalistCard`/`BrutalistButton`/`Pressable` verbatim (already in the target soft/rounded style). `BrutalistTextField` was ported but **softened on arrival** — the source file in `aavii_website` was still in the old hard-border/hard-shadow "brutalist" style, so the `vault-ui-soften` rules were applied directly during the port. `AppHeader`/`NavTabBar` were adapted, not copied verbatim: dropped the onboarding-tour hooks (`TourTargets`) and study-app branding/asset dependencies that don't apply here, rebranded, and retargeted the nav to this app's 3 screens (Upload/Approve/Query).
- **Part 3**: Node/Express backend skeleton at `server/`, same shape as Track B's proven `routes/` → `agents/` → `skills/` split, with `dotenv` wired in from the start this time (Track B's first build forgot this and it cost real debugging time).
- **Part 4**: Firebase wiring for both sides.
  - Android package renamed `com.aavii.gdg_slip_flow` → `com.aavii.gdg` to match the Android app already registered in the `gdgdeployordie` Firebase project (confirmed via the `google-services.json` you provided); `MainActivity.kt` moved to match the new package path.
  - `lib/firebase_options.dart` hand-written in the same shape the FlutterFire CLI generates — the CLI's logged-in account (`zenthros.codes@gmail.com`) doesn't have access to `gdgdeployordie` (it was created under a different Google account), so `flutterfire configure` wasn't usable. Built from the Web app config (Firebase Console → Project Settings → Web app) plus `google-services.json`.
  - `server/firebase.ts`: `firebase-admin` initialized with a service account key (`server/firebase-service-account.json`, gitignored, never committed) for server-side Firestore/Storage access. Verified with a real write-then-read-then-delete smoke test against Firestore before wiring it into any route.
  - **Real bug found and worked around**: Firebase's JS interop throws an uncaught `dartException` at runtime specifically under `dart2js` **release** compilation on this Flutter/Dart version (Flutter 3.44.8 / Dart 3.12.2) — confirmed by isolating dependencies one at a time (crash persisted with only `firebase_core` present, no `cloud_firestore`/`firebase_storage`), pinning `firebase_core` to an older stable release (3.15.2 — changed the exception but didn't fix it), and lowering `dart2js` optimization (`--dart2js-optimization=O1` — still crashed). **`flutter run` in debug mode (DDC compiler) and `flutter build web --debug` both work with no crash** — confirmed Firestore and Storage both initialize successfully. Decision: use `flutter build web --debug` as the CI/demo build target. Trade-off accepted: larger, unminified bundle — acceptable for a hackathon submission where "working software" matters more than bundle size, and reversible later if a `dart2js`-compatible plugin version surfaces.
- **Data source note**: `Airtable` was one of the two DB options left open in the original planning doc ("[Airtable/Supabase — pick one]"). Firestore was picked first since the Firebase project was already provisioned and proven working. An Airtable API key was subsequently offered as an additional/alternate data source — how it slots in (replacing Firestore vs. supplementing it, e.g. for an existing reference dataset the QueryAgent should read) will be resolved and documented here once the key and its intended use are provided.

## Time budget

Same checkpoint discipline as the approved plan: if the core flow (upload → extract → approve → query-with-citation) isn't working end-to-end with green CI by roughly the 2/3 mark of remaining time, stop adding scope and fall back to polishing/submitting Track B instead.

- **Part 6**: `SlipExtractionAgent` + `parse_slip_data` skill (see `AGENTS_AND_SKILLS.md` for the full writeup). Verified with a real synthetic test slip image (generated with PIL, not a real photo — but real handwriting-style text) before any UI was built: correctly extracted item/quantity/unit/date/supplier, both Firestore writes (`slips_pending`, `audit_log`) confirmed directly.
  - **Real bug found and fixed**: `server/firebase.ts` read `process.env.GOOGLE_APPLICATION_CREDENTIALS` at module load time, but `dotenv.config()` in `index.ts` runs *after* its imports are evaluated (imports are hoisted in both ES modules and CommonJS) — so `firebase.ts` was reading the environment before `.env` had been loaded. Same root-cause category as Track B's original dotenv bug, different manifestation (transitive import ordering rather than a missing call). Fixed by calling `dotenv.config()` directly inside `firebase.ts` itself, not relying on the entrypoint having done it first.
  - **Known gap, not blocking**: Firebase Storage returns "the specified bucket does not exist" — the bucket needs to be explicitly enabled once in the Firebase Console (Build → Storage → Get Started, which may require confirming the Blaze plan) before it's actually provisioned; having the bucket name in config isn't enough. Decision: made the Storage upload step non-blocking (`uploadSlipImage` catches and logs, returns `null` instead of throwing) so extraction and the approval workflow are fully functional without it. `imageUrl` will be `null` on records until Storage is enabled — the Approval screen should handle that (e.g. show a placeholder), and Storage should be enabled before the real demo so slip images actually show.

- **Part 7**: Upload + Approval screens (Flutter), plus `GET /api/pending-slips`, `GET /api/slips`, `POST /api/approve-slip`, `POST /api/reject-slip`. All Firestore/Storage access stays server-side — the Flutter app only ever calls the backend REST API (`lib/services/api_client.dart`), never touches Firebase directly. This was a deliberate simplification made here (not in the original plan): it means Flutter's `cloud_firestore`/`firebase_storage` packages end up unused by the actual screens (kept for now since Part 4 already proved them working and future native-Android use might want them), removes any need to write Firestore security rules (only the trusted backend, using the admin SDK, ever reads/writes), and keeps a single trusted, audit-logged path for every write.
  - **Real bug found and fixed**: an unhandled promise rejection in `server/routes/slips.ts` (no try/catch) crashed the entire backend process on a malformed request instead of returning an error response. All routes now wrapped; also hit and fixed a Git-Bash-specific `curl` quoting issue during manual testing (inline `-d "{...}"` with escaped quotes got mangled — switched to file-based `--data-binary @file` request bodies for reliable manual testing).
- **Part 8**: `QueryAgent` + `answer_from_records` skill + query screen — the second custom agent/skill pair. Verified with two real cases: a question answerable from one specific record (correctly cited only that record) and a genuinely unanswerable question (correctly refused to guess rather than fabricating an answer).
- **Part 9**: CI/CD. One GitHub Actions job: Node setup → backend lint/build → Flutter setup → `flutter analyze`/`flutter test`/`flutter build web --debug` → Playwright.
  - **Playwright coverage decision**: attempted to activate Flutter Web's accessibility/semantics DOM overlay (the mechanism that would let Playwright's normal click/fill locators drive the canvas-rendered UI) by dispatching pointer events at the `flt-semantics-placeholder` element — a bounded, ~15-minute experiment, not a deep rabbit hole given the earlier dart2js debugging already ate real time this build. It didn't reliably activate. Decision: `tests/app-loads.spec.ts` verifies the real deployed app loads without a JS/console error (genuine regression coverage — this is exactly what would have caught the dart2js crash bug earlier), and `tests/api-flow.spec.ts` drives the actual extract→approve→query and reject flows through the same REST API the UI calls, against the real Gemini API and real Firestore — turning the manual curl verification done throughout this build into permanent, CI-enforced tests. This is real coverage of the agent logic; it just isn't simulated mouse clicks on the canvas.
  - Each CI run's `api-flow.spec.ts` writes one real (correctly-extracted, not synthetic-garbage) record to `slips`/`audit_log` — there's no delete endpoint (out of scope for this build), so a manual Firestore cleanup pass happens before the final demo, not after every CI run.

## 2026-08-08 — Reframing: single-factory tool → configurable business-ops platform

After Parts 1-9 shipped a fully working single-purpose tool (raw-material intake slips only), the product direction broadened: instead of one paper-form type for one factory, build it as a platform any paper-heavy business could configure for its own registers (intake, production, dispatch, attendance, expenses, ...), demoed end-to-end on a real plastic recycling factory. Four pillars: (1) generalized paperwork digitization, (2) workforce automation (attendance + payroll), (3) an owner-facing daily digest agent, (4) a compliance document library. Kept the existing repo/name (`gdg-slip-flow`) — renaming has no functional value and the working git history matters more than the label.

- **Part 10**: Generalized the data model from a hardcoded intake-slip shape to configurable register types (`server/registerTypes.ts`) — a plain config object mapping a register type id (intake/production/dispatch/attendance/expense) to its field schema and a description used in the extraction prompt. Adding a new paper form the system can handle is now a config entry, not new agent/prompt code — this is the extensibility story that makes "usable by different companies" credible rather than just claimed.
  - `SlipExtractionAgent`/`parse_slip_data` → generalized into `RegisterExtractionAgent`/`extract_register_data`: the prompt and output schema are now built dynamically from a `RegisterTypeConfig` instead of being hardcoded to item/quantity/unit/date/supplier. Old files deleted outright (not kept alongside as a compatibility shim) — this is pre-launch code with no external callers.
  - Collections renamed `slips_pending`/`slips` → `records_pending`/`records`; every record now carries `registerType` and a generic `fields: Record<string, string|number|null>` object instead of flat named fields, plus a `companyId` (currently a single hardcoded `demo-factory` constant — see below).
  - `QueryAgent`/`answer_from_records` updated to query `records` and describe itself generically ("a business's digitized paper records... registerType") rather than assuming intake slips; citation field renamed `citedSlipIds` → `citedRecordIds` for consistency.
  - **Multi-tenancy**: every record carries a `companyId` field (`server/registerTypes.ts`'s `DEFAULT_COMPANY_ID`) so the data model is genuinely multi-tenant-ready, but there is no auth or company picker built — full tenant isolation was explicitly scoped out as too large for the remaining time. The architecture supports it; the demo doesn't exercise it.
  - Verified via the same curl-first discipline as every prior part: extract (intake type) → appears in `pending-records` → approve → appears in `records`, all against the real Gemini API and real Firestore, before touching the Flutter side (which is Part 11 — the app still calls the old `*-slip` endpoints until then and will not build against the backend until that part lands).
  - Query itself hit the pre-existing Gemini free-tier daily quota wall (20 requests/day on the current model) during this verification pass — not a regression from this change; extraction and the Firestore read/write path are unaffected.
- **Part 11**: Updated the Flutter side to match — `ApiClient` now calls the generalized `*-record` endpoints and adds `fetchRegisterTypes()`. `HomeShell` (`main.dart`) fetches register types once at startup and passes them down to `UploadScreen`/`ApprovalScreen` rather than each screen re-fetching or hardcoding a field list.
  - `UploadScreen` gained a register-type picker (pill chips) above the camera/gallery buttons; the extraction result card renders whichever fields the selected type defines, read from the type config, instead of hardcoded item/quantity/unit.
  - `ApprovalScreen`'s pending-record card builds its `TextEditingController`s dynamically from the matching register type's field list (a `Map<String, TextEditingController>` keyed by field key, not five hardcoded named controllers) — this is what makes one card widget work for intake, production, dispatch, attendance, and expense records without an if/else per type.
  - Verified end-to-end through the real running app (not just curl): loaded the built Flutter Web app against the real backend, confirmed `GET /api/register-types` succeeds and the app renders past its loading state. Full click-driven UI verification isn't reliable here (same Flutter-Web-canvas limitation as Part 9), so this pairs with `tests/api-flow.spec.ts` (updated to the new endpoint/field shapes) as the actual regression coverage of the underlying logic.

## Open risks

- The `dart2js` release-mode Firebase crash (see Part 4) — mitigated by using `--debug` builds, but worth re-testing if Flutter/Firebase plugin versions change.
- Firebase CLI on this machine can't directly manage the `gdgdeployordie` project (different Google account) — any future FlutterFire CLI regeneration needs to happen from the account that owns the project, or config needs to keep being hand-maintained.
- Firebase Storage bucket not yet enabled in the console (see Part 6) — extraction works, but slip images won't actually display until this is done.
